# Voxamber repository workflow

- The latest user-approved product flow is import-first: users obtain scene code from their own high-capability LLM apps, import by paste/file/system sharing, and this App compiles, previews, edits, saves and exports locally using Google's native SDK. A local foundation-model download is no longer a required onboarding or release gate for that flow. Do not restart local-model selection or diffusion experiments as the primary task.
- The user clarified on 2026-11-06 that the goal is Google Three-Live's programmatic scene-building workflow running locally through a native iPhone integration. Image diffusion followed by Hunyuan mesh generation was an agent-selected detour, rejected as the primary product architecture. Do not resume its downloads, uploads, default selection or release work automatically.
- The existing `ThreeLiveNative` package is a Swift geometry serializer, not Google's compiler. The palace PoC used an agent-authored host geometry generator followed by the actual Google compiler; it does not prove that an on-device small model can independently author the same scene. Preserve that distinction when planning or reporting results.
- Preserve `Apple/.build/Phone6Recovery` and `Apple/.build/Preserved-2026-11-06`: they contain the latest confirmed user-project backup, one verified Qwen model copy, the released build-6 IPA, and incomplete-upload state. They are retained data, not disposable build caches. Use one shared dependency/build location for further work; do not recreate many complete experimental build trees.
- This project is a general on-device 3D modeling app. Do not constrain creation to buildings, furniture, or a fixed object category list. Examples are inspiration only.
- Product names: 维珀 / Voxamber. Bundle: `com.kaisun.voxamber`. Category: Productivity.
- Use native Swift, MLX, Metal, and Apple frameworks. Do not embed Python or unrelated external script runtimes. On 2026-11-06 the user explicitly allowed the restricted scene engine bundled inside Google's official native Three-Live SDK. That SDK is the approved exception to the earlier JavaScript-engine prohibition; do not replace it with a WebView or another general script engine.
- Target iPhone devices with at least 12GB RAM and adaptive iPhone Duo interfaces. On-device foundation models must remain in the 8B class or smaller; verify actual model suitability and performance rather than assuming newer or larger is better.
- `dev` is the local working branch and GitHub default development branch. Make ongoing development commits and pushes there.
- `main` is the release branch. Merge a verified release from `dev` and push `main` once per release; do not merge unfinished development into it. Initial repository setup is the only bootstrap exception.
- Keep model weights, build outputs, local caches, credentials, signing keys, provisioning profiles, and raw logs out of Git. Commit pinned public model manifests, source, licenses, tests, and sanitized verification receipts.
- Keep package tests, Simulator checks, real-device inference, offline acceptance, archive/upload, Apple processing, and TestFlight availability as separately evidenced states. Do not report one as proof of another.
- Never use `devicectl device copy to --remove-existing-content true` for a real app data container. In this environment it cleared the app data domain even with a nested destination. Omit that option for all transfers; do not use it for cleanup.
- Before removing device test files, take and verify a fresh backup of current user projects and draft. Restore only the latest known current project IDs; never merge older snapshots or resurrect the user's deleted projects. Verify restored files by copying them back and comparing every hash.

- Preserve `/Users/kaisun/Library/Application Support/Voxamber/Signing`: it contains persistent signing credentials, profiles and the dedicated signing keychain. Never treat it as an experiment cache or copy its secrets into Git.
